# 개발 방식

## 원칙
- 처음부터 완벽하게 만들지 않고 MVP에서 점진적으로 발전시킨다. 그 과정에서 생기는 문제를 트러블슈팅으로 기록한다.
- AI가 만든 코드라도 설명하지 못하는 코드는 머지하지 않는다.

## 기능 하나를 만드는 사이클
1. 명세: 기능 명세와 완료 기준 확정 (정책은 사람이 결정)
2. 계획: 계획 모드에서 구현 계획을 받고 검토, 수정
3. 테스트 먼저: 완료 기준을 테스트로 옮긴다
4. 구현: 테스트 통과까지 반복, 테스트 출력으로 확인
5. 독립 리뷰: 새 컨텍스트의 리뷰어가 변경분만 검토. 정확성, 요구사항 문제만 지적
6. 이해 확인: 변경분을 설명할 수 있는지 확인
7. 커밋, PR: 무엇을, 왜, 어떻게 검증했는지
8. 하네스 개선: AI가 틀린 것을 규칙, 훅, 스킬에 반영하고 기록

- 직접 설계할 것: 참가와 정원 초과 방지, 매치 상태 전환과 자동 확정·취소, 빈자리 알림 흐름, 결제 승인
- 맡겨도 되는 것: DTO, 단순 조회 API, 설정, 프론트 화면 대부분, 테스트 데이터 (이해 확인은 동일)

## AI 작업 원칙
- 검증 수단(테스트, 빌드)을 먼저 주고 결과를 보여 달라고 한다
- 탐색 → 계획 → 구현 → 커밋. 한 문장으로 설명되는 작은 수정은 바로 진행
- 작업마다 대화를 비운다. 같은 문제를 두 번 고쳐도 안 되면 새로 시작
- 작업을 요청할 때 필요한 문서를 직접 지정한다

## 하네스는 필요할 때마다 키운다
| 시점 | 추가할 것 | 계기 |
|---|---|---|
| 저장소 세팅 | 짧은 CLAUDE.md, 권한 설정(비밀값 읽기 금지) | 기본 |
| 개발 시작 | `.claude/rules/` 로 backend, frontend 규칙 분리(paths 지정), 포맷 훅 | 코드 작성 시작 |
| 첫 기능 완성 후 | 리뷰어 서브에이전트, 작업 종료 시 테스트를 돌리는 훅 | 검증을 매번 직접 하기 번거로울 때 |
| API 연동이 반복될 때 | API 연동 스킬: OpenAPI → 타입 → Axios 함수 → TanStack Query 훅 → 테스트. 전처리 스크립트로 필요한 정보만 넘기고 전후 비교 | 같은 요청을 세 번째 쓸 때 |
| 반복 절차 | `/spec-to-test`, `/troubleshoot` 스킬 | 같은 절차를 반복할 때 |
| CI 구축 | GitHub Actions PR 자동 리뷰 | PR 단위로 일할 때 |
| 성능, 장애 | 읽기 전용 DB MCP, 원인이 불분명한 장애에 에이전트 팀(선택) | 원인이 하나로 좁혀지지 않을 때 |

피할 것: CLAUDE.md에 다 써넣기, 리뷰어 지적 전부 반영하기, 한 대화에 여러 작업 섞기, 처음부터 전부 자동화하기, 의사코드 수준의 명세

## 문서 규칙
- 기능 명세는 `docs/spec/spec.md` 한 파일로 시작한다. 커지면 도메인별로 나누고, 나누기 전후를 `/context` 로 측정해 `docs/ai-log.md` 에 남긴다
- 중요한 기술 결정은 `docs/adr/` 에 하나씩 남긴다. 결정이 바뀌면 기존 ADR은 고치지 않고 새 ADR을 쓰고, 이전 것은 "대체됨"으로 표시한다
- 파일 이름은 영어, 내용은 한국어

## 기록
- 트러블슈팅 (`docs/troubleshooting/`): 문제 → 원인 추정 → 측정 → 적용 → 개선 수치
- 기술 도입: 왜 필요했는지, 대안, 도입 전후 수치
- `docs/ai-log.md`: 날짜, AI가 틀린 것, 조치(규칙, 훅, 스킬)
- `docs/til/`: 새로 이해한 개념

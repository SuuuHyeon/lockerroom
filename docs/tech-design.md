# 기술 설계

버전 선택 이유는 `docs/adr/` 참고.

## MVP 스택
| 영역 | 기술 |
|---|---|
| 백엔드 | Java 21, Spring Boot 4.1, Spring Data JPA |
| DB | MySQL 8.4 LTS |
| 인증 | Spring Security, JWT, 카카오 로그인 |
| 프론트 | React + Vite (SPA), TypeScript, React Router, TanStack Query + Axios, Tailwind CSS, vite-plugin-pwa. 전역 상태는 필요할 때 Zustand |
| 푸시 | Firebase Cloud Messaging 웹 푸시 |
| 배포 | Docker, Docker Compose, Nginx, GitHub Actions, AWS EC2. 도메인 + HTTPS 필수 (웹 푸시, PWA는 HTTPS에서만 동작) |
| API 문서 | springdoc(OpenAPI). 프론트 타입 생성에도 사용 |

## 핵심 기술 과제
- 정원 초과 방지: 동시 신청이 몰려도 최대 인원을 넘지 않게. MVP는 DB 락으로 시작하고, 이후 Redis, 대기열 순서로 한 단계씩 개선하며 전후를 측정한다
- 자동 확정, 취소: 스케줄러. 서버가 여러 대일 때 중복 실행되지 않게 한다
- 알림: 참가 처리와 알림 발송을 분리한다 (트랜잭션 이후 이벤트, 비동기). 이벤트와 발송을 분리해 두어 Kafka 도입, 알림 종류 추가가 쉽게 한다

## 단계별 도입 (문제가 보일 때 붙인다)
| 순서 | 기술 | 어디에 쓰나 | 도입 계기와 측정할 것 |
|---|---|---|---|
| 1 | Actuator, Micrometer, Prometheus, Grafana, k6 | 모니터링, 부하 테스트 | MVP 배포 직후. p95 응답 시간, 에러율, DB 커넥션 풀 기준선 측정 |
| 2 | Redis | 정원 차감, 대기열, 매치 목록 캐싱, 중복 알림 방지 | 새 날짜 오픈 시각에 신청이 몰릴 때. DB 락과 비교해 처리량, 응답 시간, 정원 정확성 측정 |
| 3 | Kafka | 참가, 취소, 확정, 자동 취소 이벤트 → 알림 소비자. 재시도, 실패 메시지 보관 | 알림 발송이 신청 처리를 느리게 할 때. 신청 응답 시간과 알림 지연 측정. 아웃박스 패턴 검토 |
| 4 | Elasticsearch | 매치, 구장 검색 (지역, 시간, 형식, 위치) | 데이터가 많아질 때. 샘플 대량 데이터로 MySQL 검색과 비교 |
| 5 | Kubernetes | Docker 이미지를 여러 개 띄우기, 자동 복구, 무중단 배포 | 마지막. 로컬(kind 등)에서 먼저 |
| 필요 시 | Spring Batch | 통계, 오래된 데이터 정리 | 스케줄러로 부족해질 때 |
| 추후 | SSE 또는 WebSocket | 매치 상세의 남은 자리 실시간 갱신, 구장별 채팅 | 해당 기능을 만들 때. WebSocket, SSE, 폴링 비교 |
| 추후 | 슬랙, 지라 | 장애, 배포 알림. 이슈 관리 | 모니터링 도입 시 |
| 추후 | Spring AI | 자연어 매치 검색 | 핵심 백엔드 기술 이후 |

- 이 규모에서는 Kafka, Elasticsearch 없이도 서비스가 돈다. "이런 문제가 생겨서 도입했고 전후를 측정했다"로 기록한다.
- 작은 EC2에서는 Kafka, Elasticsearch가 메모리를 많이 쓴다. 실험은 로컬 Docker Compose에서 한다.

## 결제 (1.5단계)
- 토스페이먼츠 테스트 키 (회원가입만으로 발급, 실제 청구 없음)
- 흐름: 결제 요청(프론트) → 성공 리다이렉트 → 서버에서 결제 승인 API 호출
- 다룰 문제: 금액 위변조 검증, 참가와 결제의 정합성(실패 시 되돌리기), 결제 중 자리 임시 점유와 만료, 중복 승인 방지(멱등성), 취소 시점별 환불, 자동 취소 시 일괄 환불

## 테스트 전략
| 종류 | 대상 | 도구 |
|---|---|---|
| 단위 | 참가 규칙, 취소 가능 여부, 매치 상태 전환. 시간에 따라 달라지는 로직은 현재 시각을 주입받게 만들어 테스트 | JUnit 5, AssertJ, Mockito |
| 통합 | 저장소 쿼리, 트랜잭션 | Spring Boot Test, Testcontainers(MySQL) |
| 동시성 | 정원 1자리에 동시 신청 시 한 명만 성공, 정원을 넘지 않음 | 멀티 스레드 테스트 |
| API | 요청, 응답, 에러 코드 | MockMvc |
| 외부 연동 | 토스 승인, FCM 실패 상황 재현 | WireMock |
| E2E | 로그인 → 참가 → 취소 → 대기자 알림 → 재참가 (테스트 환경은 대체 로그인) | Playwright |

- 기능 명세의 완료 기준을 그대로 테스트로 옮긴다
- CI에서 테스트가 실패하면 머지하지 않는다
- 커버리지(JaCoCo)는 핵심 도메인(참가, 결제) 위주로 본다
